PROPOSED SOLUTION

Misconfiguration, not zero-days, causes ~99% of firewall breaches. Yet every device from 40+ vendors is still hardened by hand, one CLI at a time.
① ANY VENDOR CONFIG IN → ONE HARDENING REPORT OUT
② PROPRIETARY SYNTAX → ONE VENDOR-NEUTRAL MODEL
③ WHY IT MATTERS
✦ Proposed Solution (Describe your Idea / Solution / Prototype)

Detailed explanation: Walrus ingests any network-device config from Cisco, Juniper, Arista, Palo Alto, firewalls, switches, cloud security groups. The AI reads it into one vendor-neutral Security Baseline Model; a deterministic engine then checks every control from CIS, NIST SP 800-53, DISA STIG and ISO 27001 and emits a per-device PDF with pass/fail, severity and the exact fix commands.

How it addresses the problem: It replaces slow manual checklist auditing and rigid, vendor-locked suites with one source of truth across a heterogeneous fleet. An unseen vendor is taught through a low-code training GUI, with no code redeploy.

Innovation and uniqueness: The AI only parses; the verdict is deterministic and every finding cites its exact config line, so it never hallucinates a pass/fail. A checklist gate makes it structurally unable to skip a control.

TECHNICAL APPROACH

Orchestrator → queue → a fleet of workers that pull work, each with its own harness and one shared live ledger, built so it cannot skip a single control.
① THE ENGINE · WORKERS PULL, LEDGER TRACKS, NOTHING CLASHES
② THE AI PIPELINE · ONE CONFIG'S JOURNEY, WITH A LEARN LOOP
③ FOUR STAGES, END TO END
✦ Technical Approach

Technologies used: Config collection via Netmiko / NAPALM, upload or a config repo; an open-weight LLM (NLP + pattern) for parsing, run on-prem; a deterministic rules engine over a control knowledge base (CIS / NIST 800-53 / STIG / ISO 27001); ReportLab for the per-device PDF. Built on the Walrus Harness engine.

Methodology and process: The orchestrator writes one task per device to a queue; workers pull work, each running the harness, and a shared live ledger shows who is doing what and lets workers pause on a clash. When a config cross-references another object such as a nested ACL or a linked device, it is re-queued and run through the full control set, so coverage never leaks.

Never miss, never lie: The knowledge base is the checklist. The fleet must return a verdict for every applicable control before an audit can close; the model only proposes fields, the engine decides, and every verdict is backed by an append-only evidence log.

✦ Feasibility and Viability

Feasibility: The orchestration, evidence and checklist engine already exists (Walrus Harness). Netmiko/NAPALM and the four frameworks are mature and public; an open-weight model runs on a mid-range GPU on-prem. Deployable on an air-gapped server, private cloud or a single laptop.

Potential challenges and risks: Unseen vendor firmware breaks fixed parsers · an LLM can hallucinate · a 10,000-device fleet is slow to audit by hand · configs cross-reference each other.

Strategies for overcoming them: Unknown vendor → train via GUI, zero code. Hallucination → deterministic check + cited evidence, no model on the verdict. Scale → queue + worker fleet, in parallel. Cross-references → re-queued through the full control set. And nothing leaves the building with no external calls, fit for NCIIPC-class infrastructure.
